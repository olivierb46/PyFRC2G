# How PyFRC2G works and how to read the results

This document explains **what the application does**, **how it reaches its results** and **how to
read them**. It is written for network administrators, security officers (CISO) and auditors who
receive the reports. Installation and detailed options are in `web/README.md` (web application) and
`engine/README.md` (command line engine).

## 1. Overview

PyFRC2G reads the rules of a firewall, converts them to a common format, **audits** them,
computes a **risk score**, detects the **changes** since the previous analysis, then produces
reports (PDF, HTML, Excel, CSV, graphs) and, if you want, sends the PDF as **evidence** to
CISO Assistant.

```
Source                    Engine                                      Results
─────────────────────     ─────────────────────────────────────────   ─────────────────────────
pfSense / OPNsense API ─┐ 1. Read and normalise the rules             Risk score (0-100)
Configuration file     ─┴▶ 2. Changes since previous analysis    ───▶ Audit findings
 (pfSense, OPNsense,      3. Audit + policy + unused rules            Changes
  FortiGate, iptables,    4. Exceptions (accepted risks)              Zone matrix
  nftables, Stormshield)  5. Risk score, zone matrix                  Graphs, NAT, rule usage
                          6. PDF / HTML / Excel / CSV reports         Reports + CISO evidence
```

There are two ways to use it:

- **The web application** (`web/`): dashboard, history, comparison, exceptions, exports,
  upload to CISO Assistant. Everything is stored **encrypted** in a SQLite database.
- **The command line engine** (`engine/`, command `pyfrc2g`): same analyses and same reports,
  written to a folder, without any interface.

The web application runs the engine: both give the same results.

## 2. Where the rules come from

| Source | How | Notes |
|--------|-----|-------|
| **Firewall API** | pfSense (REST API v2 package), OPNsense or nfSensei (API key): the application queries the firewall, read only (the running configuration by default, not the uncommitted candidate one) | Manual or scheduled analysis. Allows reading the rule hit counters (nfSensei: only for rules with counters enabled). |
| **Configuration file** (backup) | pfSense / OPNsense `config.xml`, FortiGate `.conf`, `iptables-save -c`, `nft -j list ruleset`, nfSensei backup (`running.yaml`, or the whole backup archive of which only `running.yaml` is kept), Stormshield archive | No access to the firewall needed. The file is stored encrypted and can be analysed again. |

In both cases every rule becomes one row with the same columns: interface, action
(pass / block / reject), source, destination, protocol, port, comment, IPv4/IPv6, disabled or
not, floating or not, **automatic** (generated by the firewall itself, e.g. the default OPNsense
rules), hit counters.

Aliases (lists of addresses or ports) are **resolved**, so that the audit reasons on the real
addresses and ports.

## 3. What an analysis does

1. **Reading** of the rules, aliases, NAT rules and, when possible, the rule hit counters. When several API firewalls are analysed in one run, they are read in parallel (4 at a time by default, `--workers` / Settings); the following steps run one firewall after the other.
2. **Fingerprint**: a SHA-256 signature of the rules. For an API firewall, when nothing has
   changed since the last analysis, the analysis stops ("no change") and nothing is stored. A
   configuration file is always analysed.
3. **Changes**: comparison with the previous analysis (rules added, modified, removed).
4. **Audit**: checks on each rule and between rules (section 4).
5. **Compliance policy**: your own business rules (section 6).
6. **Exceptions**: accepted risks are taken out of the findings (section 7).
7. **Risk score** and **zone matrix** (sections 5 and 8).
8. **Reports**: CSV, PDF, HTML, Excel, graphs. The PDF can be sent to CISO Assistant.

## 4. Audit findings

Every finding has a **severity** (CRITICAL, HIGH, MEDIUM, LOW), a **check** (its name), the rule
concerned (interface, order number, identifier, text) and a **detail** in plain text.

| Check | Severity | What it reports |
|-------|----------|-----------------|
| `ANY_ANY` | CRITICAL | Any source to any destination, any protocol and port |
| `ANY_ANY` | MEDIUM | Same, but limited to one protocol or some ports |
| `WAN_EXPOSED` | CRITICAL | Firewall administration exposed to the Internet (administration ports) |
| `WAN_EXPOSED` | HIGH | Administration or sensitive ports open from the Internet, or all ports open |
| `SHADOWED` | MEDIUM | Rule never reached: an earlier rule already decides the same traffic |
| `REDUNDANT` | LOW | Rule already covered by an earlier rule with the same action |
| `PARTIAL_OVERLAP` | LOW | Part of the traffic is already decided by an earlier rule |
| `DISABLED` | LOW | Disabled rule still present |
| `NO_DESCRIPTION` | LOW | Rule without comment: its purpose cannot be audited |
| `UNUSED` | MEDIUM | No packet ever matched the rule over N days of observation |
| `NO_RECENT_TRAFFIC` | LOW | No new packet for N days |
| `POLICY:<id>` | as set by the policy | Violation of a rule of your compliance policy |

Good to know:

- **Automatic** rules (generated by the firewall) get no finding of their own.
- Administration ports, sensitive ports and "Internet" interfaces are **configurable** (globally
  or per firewall): `WAN_EXPOSED` depends directly on them.
- `UNUSED` and `NO_RECENT_TRAFFIC` need **hit counters** and **time**: the engine keeps a history
  and only concludes after the configured number of days.
- A finding is a **signal to examine**, not a verdict: an `ANY_ANY` rule may be intended (that is
  what exceptions are for, section 7).

## 5. The risk score

The score goes from **0 (no problem) to 100**. It is computed from the **active** findings (those
that are not accepted risks):

| Severity | Points per finding |
|----------|--------------------|
| CRITICAL | 25 |
| HIGH | 10 |
| MEDIUM | 4 |
| LOW | 1 (LOW findings count for **10 points at most** in total) |

The total is capped at 100. Example: 1 CRITICAL + 2 HIGH + 3 MEDIUM + 30 LOW = 25 + 20 + 12 + 10
= **67**.

| Score | Level |
|-------|-------|
| 60 to 100 | CRITICAL |
| 30 to 59 | HIGH |
| 10 to 29 | MODERATE |
| 0 to 9 | LOW |

The score is also computed **per interface**. The **trend** ("+5 since previous") and the history
chart show whether the situation improves. Without any change the score stays the same: only a
change of the configuration, the policy, the audit settings or the exceptions moves it.

## 6. Compliance policy

A policy is a YAML file with your internal rules, for example "RDP must never be reachable from
the Internet" or "every pass rule must be documented". Each violation becomes a
`POLICY:<identifier>` finding with the severity you chose.

It can be defined at three levels, which add up:

1. **Global** (Administration > Settings), or **specific to a firewall** instead of the global one.
2. **Per site** and **per tag** (Administration > Policies): added to the firewalls whose *Site*
   or one of whose *Tags* matches.
3. "**No policy**" on a firewall turns everything off.

Commented example: `engine/examples/policy.example.yml`.

## 7. Accepted risks (exceptions)

A finding can be **accepted**: the risk is known and justified (legacy VPN, end-of-life
equipment...). From the **Audit** tab of a firewall, an administrator gives:

- the **justification** (required), an **owner** and an **expiry date** (optional);
- the scope: **this rule only** or **every rule** raising this check;
- **this firewall** or **all firewalls**.

Effect:

- the finding **leaves** the list of findings, the severity counts and the **score**;
- it is listed apart, in an **"Accepted risks"** section with its justification, owner and expiry
  (application, PDF, HTML, Excel, `_ACCEPTED.csv`): nothing is hidden, it is filed separately;
- on the **expiry date** the finding counts again;
- adding or removing an exception **regenerates the reports** of the firewalls concerned, so that
  they stay consistent with the application.

On the command line: `pyfrc2g --backup config.xml --exceptions exceptions.yml`
(example: `engine/examples/exceptions.example.yml`).

## 8. The zone matrix

A **source zone × destination zone** table answering "can traffic go from A to B?". The zones are
the interfaces, plus **Firewall** (the firewall itself) and **Internet**.

| Status | Meaning |
|--------|---------|
| **ALLOWED** | All traffic is allowed by one rule |
| **PARTIAL** | Only some hosts or services get through (rule numbers and services listed; `?` = alias or interface not fully resolved) |
| **BLOCKED** | No pass rule: the traffic is refused |
| **-** | Same zone |

It only covers IPv4 traffic and the firewalls whose rules are attached to an ingress interface
(pfSense, OPNsense, FortiGate, nfSensei). Non-"quick" rules (pf last matching rule) only decide when no
"quick" rule matches.

## 9. Rule usage (hit counters)

When counters are available (OPNsense through the API, pfSense through `--hits api` or a
`pfctl -vvsr` file), every rule gets a status:

| Status | Meaning |
|--------|---------|
| **ACTIVE** | Recent traffic matched |
| **NO HIT YET** | No traffic yet, but observed for less than N days: too early to conclude |
| **STALE** | Traffic in the past, nothing for N days (`NO_RECENT_TRAFFIC` finding) |
| **UNUSED** | Never any traffic over N days (`UNUSED` finding): candidate for removal |
| **DISABLED** | Disabled rule |

Counters are packet counts: their evolution alone does not trigger a new analysis.

## 10. Changes

At every new analysis the rules are compared with the previous one:

- **ADDED**: rule added;
- **REMOVED**: rule removed;
- **MODIFIED**: rule modified (the detail lists `field: before -> after`).

The first analysis of a firewall has nothing to compare with ("first analysis"). A rule is
recognised by its identifier when the firewall provides one, otherwise by its content: a simple
reordering is not a modification.

## 11. Comparing

The **Compare** page puts side by side:

- **two firewalls** (e.g. CARP primary / secondary, pre-production / production);
- or **two analyses of the same firewall** (before / after a change), with the *compare with the
  previous one* link of the history.

Result: the rules and NAT rules present only in A, only in B, or different, and the findings that
differ, with both scores.

## 12. The reports

For every firewall, in the application (firewall page, *Reports & files* tab) or in the output
folder of the engine:

| File | Content |
|------|---------|
| `<FW>_FLOW_MATRIX.pdf` | **Full report**: summary (metadata, score, rules per interface), changes, audit, accepted risks, zone matrix, rule usage, NAT, graphs. This is the PDF sent to CISO Assistant. |
| `<FW>_<interface>_FLOW_MATRIX.pdf` | Summary and graphs of one interface only |
| `<FW>_REPORT.html` | Self-contained interactive report (filterable tables) |
| `<FW>_FLOW_MATRIX.xlsx` | Excel workbook: summary, rules, audit, accepted risks, changes, matrix, usage, NAT |
| `<FW>_ALL_flows.csv` | All the normalised rules (also the snapshot used for the changes) |
| `<FW>_AUDIT.csv` | Active findings |
| `<FW>_ACCEPTED.csv` | Accepted risks (only when there are some) |
| `<FW>_CHANGES.csv` | Changes since the previous analysis |
| `<FW>_NAT.csv`, `_HITS.csv`, `_MATRIX.csv` | NAT rules, rule usage, matrix |
| Graphs (SVG) | Zones view and one graph per interface (flows rule by rule) |

The **metadata** of every report gives the integrity proof: the SHA-256 fingerprint of the rules
(and of the backup file, if any), the date, the source and the score.

## 13. The web application

| Page | What it is for |
|------|----------------|
| **Dashboard** | One firewall = one card (score, trend, rules, findings). Filters by site and tag. Excel and PDF export of all the firewalls shown. |
| **Firewall page** | Overview, rules, audit (and acceptance of a finding), changes, NAT, matrix, usage, graphs, reports, history. |
| **Configuration files** | Upload a file (with name, site and CISO ids if you want); every firewall coming from a file has its own **Settings** page. |
| **Compare** | Comparison of two firewalls or two analyses. |
| **Analyses** | Journal of the analyses, with their live log. |
| **Administration** | API firewalls, global settings, policies per site / tag, accepted risks, CISO Assistant, users, event log. |

Two roles: **admin** (configures, analyses, accepts risks) and **viewer** (reads the results and
the reports).

**Settings**: every firewall can override the global settings (Internet-facing interfaces, ports,
policy, schedule, retention, reports, CISO Assistant, site, owner, tags). An empty field uses the
global setting.

**Multi-firewall export** (from the dashboard, with its filters):

- **Excel**: *Summary* (one firewall per row), *Findings*, *Accepted risks*, *Changes* sheets;
- **PDF**: summary for management reviews (average score, firewalls, critical and high findings,
  accepted risks).

## 14. Sending to CISO Assistant

The full PDF is sent as a **new revision of an evidence** (compliance proof). The upload is manual
(button on the firewall page) or automatic after every new analysis.

Where does the proof go?

- **Evidence**: the one of the firewall, otherwise the default evidence.
- **Folder (domain)**: the one of the firewall; otherwise the one of its **site** (the
  *site = folder* table in Administration > CISO Assistant); otherwise the default folder. Useful
  when a firewall belongs to another site.
- **Change report** (option): the CSV of the changes goes to a second evidence (the one of the
  firewall, otherwise the default one).

The history of the uploads (successful or failed, with the message) is shown on the firewall page
and in Administration > CISO Assistant. The token is encrypted and never displayed again.

## 15. Security and data

- Firewall credentials, CISO token, policies, uploaded files and analyses are **encrypted** in the
  database with the application key (`PYFRC2G_SECRET_KEY`, keep it apart from the database:
  without it the data cannot be read).
- Analyses run in a private temporary folder that is deleted afterwards.
- An **event log** keeps the sign-ins, changes, uploads, accepted risks and exports.
- The number of analyses kept per firewall is limited (retention); the oldest ones, with their
  reports, are deleted.

## 16. Limits

- The audit analyses **the rules**, not the actual traffic nor the vulnerabilities of the
  firewall: a low score does not prove that a network is safe, it says that the rules read are
  clean with regard to the checks above.
- Nested or unresolved aliases can make some checks uncertain (the engine prefers not to conclude
  rather than report wrongly).
- The zone matrix only covers IPv4.
- An `UNUSED` rule is only reported after the observation period: a firewall that has just been
  added will not have any right away.
- A configuration file contains neither the automatic OPNsense rules nor the hit counters: the
  results of a backup and of the API can differ (see the "rules generated by the firewall"
  option).
- Expired exceptions only come back in the PDF reports at the next analysis (the application shows
  them immediately on the firewall page).
